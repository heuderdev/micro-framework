AlpineForm: documentação técnica

Micro-framework declarativo de formulários sobre Alpine.js 3. Regras, mensagens, máscaras e comportamento de envio são declarados nos próprios elementos HTML; um controlador por <form> descobre os campos, valida, serializa, envia com progresso real e associa a resposta do servidor aos campos.

Este documento foi escrito a partir do código-fonte deste repositório (pacote alpine-form, versão 1.0.0 em package.json e VERSION em src/index.js). Referências apontam para arquivo e símbolo; números de linha não são usados porque mudam a cada edição. Não existe arquivo vigia-laravel.js neste projeto; o suporte a Laravel é o adaptador de resposta laravelResponseAdapter em src/transport/response.js.

Convenções usadas

executável exemplo que existe em examples/ e roda contra o backend de referência. ilustrativo trecho para explicar um conceito; não é um arquivo do projeto. "Comportamento" descreve o que o código faz; "consequência" descreve um efeito observável de uma escolha, sem atribuir intenção ao autor.

1. Visão geral #

Propósito e problemas resolvidos

Formulários reais repetem os mesmos problemas: validar enquanto o usuário digita sem ser invasivo, combinar regras entre campos, consultar o servidor sem aplicar respostas antigas, formatar documentos e moedas sem corromper o valor enviado, enviar arquivos mostrando progresso verdadeiro e entender respostas de backends diferentes. O AlpineForm concentra esse comportamento em um controlador por formulário configurado por atributos HTML.

  • Declarativo: data-form-v="required|min:3" no input; nenhum campo é registrado em JavaScript.
  • Estrito: atributo ou regra desconhecida é erro de configuração visível, nunca ignorado (Field.checkUnknownAttributes, parseRules).
  • Fiel ao HTML: a serialização segue o algoritmo de lista de entradas do HTML (ordem, nomes repetidos, submitter).
  • Honesto sobre o que não sabe: progresso sem total é "indeterminado"; timeout depois do upload é "resultado desconhecido"; rede indisponível na validação remota é "inconclusivo".

Cenário de uso

Páginas renderizadas no servidor (PHP, Laravel, Joomla e similares) que já usam ou podem usar Alpine.js, com formulários de cadastro, edição, upload e importação. O projeto inclui um backend PHP de referência (server/) que implementa todos os contratos usados pelos exemplos e testes.

O que a biblioteca não pretende fazer

  • Não substitui a validação do servidor: todo envio deve ser revalidado no backend.
  • Não renderiza formulários a partir de esquemas (JSON Schema etc.): o HTML é a fonte da estrutura.
  • Não gerencia rotas, sessões ou autenticação; apenas lê o token CSRF de uma meta tag e interpreta respostas 401/403/419.
  • Não reenvia POST automaticamente após resultado desconhecido (src/transport/retry.js, comentário de política).
  • Não oferece progresso de upload por arquivo dentro de um único multipart (limitação do navegador; ver progresso).

2. Início rápido #

Instalação real

O pacote não está publicado em registro público neste repositório; ele é construído localmente:

npm install
npm run build        # gera dist/ (ESM, IIFE e IIFE minificado) via build.mjs (esbuild)

Arquivos gerados por módulo (build.mjs): dist/<nome>.esm.js, dist/<nome>.js e dist/<nome>.min.js, para alpine-form, alpine-form-masks, alpine-form-chunks, alpine-form-inspectors, alpine-form-bootstrap, alpine-form-rascunho, alpine-form-lista, alpine-form-opcoes, alpine-form-preencher, alpine-form-avisos e alpine-form-autocompletar, além do pacote único alpine-form-completo (src/completo/: núcleo com todos os módulos aplicados por AlpineForm.use). CSS opcional em css/alpine-form.css.

Ordem de carregamento

Com <script> clássico, a ordem é obrigatória: núcleo → módulos opcionais → Alpine com defer. O motivo está em src/cdn.js: o núcleo define window.AlpineForm e registra o plugin no evento alpine:init; os módulos opcionais usam window.AlpineForm; o Alpine dispara alpine:init ao iniciar.

<script src="/dist/alpine-form.min.js"></script>
<script src="/dist/alpine-form-masks.min.js"></script>      <!-- opcional -->
<script defer src="/vendor/alpine.min.js"></script>

Com ESM (é o que examples/esm-boot.js faz):

import Alpine from 'alpinejs'
import AlpineFormPlugin, { AlpineForm } from 'alpine-form'
import masks from 'alpine-form/masks'

AlpineForm.use(masks)
Alpine.plugin(AlpineFormPlugin)
Alpine.start()
Atenção

Se o Alpine já tiver iniciado quando o núcleo carregar, src/cdn.js registra o plugin mas avisa no console: formulários já processados não serão inicializados.

Menor exemplo funcional ilustrativo

<form x-data x-form action="/api/cadastro" method="post" novalidate>
    <label for="nome">Nome</label>
    <input id="nome" name="nome" data-form-v="required|min:3">
    <button type="submit" :disabled="$form.submitting">Enviar</button>
    <p data-form-status></p>
</form>

Resultado esperado: nenhuma mensagem ao carregar. Ao sair do campo com "ab", aparece "Digite pelo menos 3 caracteres." logo após o input, que recebe aria-invalid="true" e aria-describedby apontando para a mensagem. Corrigindo, a mensagem some durante a digitação (após o debounce de 200 ms). No envio, a requisição sai por XHR com cabeçalho CSRF (se houver <meta name="csrf-token">), e [data-form-status] mostra a fase.

novalidate desliga as mensagens nativas do navegador para que só a biblioteca as mostre. x-data é necessário porque o Alpine só processa diretivas dentro de componentes.

Executando os exemplos

npm run serve                 # php -S 127.0.0.1:8080 server/router.php
# abra http://127.0.0.1:8080/examples/
php server/bin/worker.php     # outro terminal, apenas para o exemplo de processamento

Requisitos: Node ≥ 18 e PHP ≥ 8.1. O roteador (server/router.php) serve /api, /examples, /dist, /css, /doc.html, /docs e /vendor (mapeado de node_modules).

3. Anatomia de um formulário #

Trecho real de examples/cadastro.php (abreviado; "…" marca omissões):

<form id="cadastro" x-data="{ tipo: 'pf' }" x-form action="/api/cadastro" method="post"
      data-form-validation="live" data-form-debounce="250" data-form-idempotency novalidate>
    <input id="nome" name="nome" data-form-v="required|min:3|max:120"
           data-form-msg.required="Informe seu nome."
           data-form-msg.min="Digite pelo menos :min caracteres.">
    <input id="email" name="email" type="email" data-form-v="required|email"
           data-form-remote="/api/validar-email" data-form-msg.remote="Este e-mail já está cadastrado.">
    <input id="cpf" name="cpf" data-form-mask="cpf" data-form-v="required|cpf" data-form-submit-value="raw">
    …
    <input name="cnpj" data-form-mask="cnpj" data-form-v="required_if:tipo,pj|cnpj" data-form-submit-value="raw">
    <button type="submit" :disabled="$form.submitting">Cadastrar</button>
    <p data-form-status class="hint"></p>
</form>
<form>
Precisa ser um HTMLFormElement (o construtor de FormController recusa outro elemento) e não pode estar dentro de outro form.
x-form
Diretiva registrada em AlpineFormPlugin. A expressão opcional é avaliada pelo Alpine e deve resultar em objeto simples de opções.
data-form-* no form
Configuração do formulário (modo de validação, debounce, transporte, adaptador…). Ver atributos.
Inputs
Todo input/select/textarea com name vira campo (exceto botões e data-form-ignore). Radios e checkboxes de mesmo nome formam um grupo.
Mensagens
data-form-msg.<regra> sobrescreve a mensagem padrão; :min e similares são substituídos.
Estado
$form é o objeto reativo do formulário ($form.submitting, $form.errors…).
Submit
O evento submit é interceptado (FormController.onSubmit), a validação completa roda e o envio é feito por transporte.
Progresso e cancelamento
Elementos [data-form-progress*], [data-form-status] e botões [data-form-cancel] são atualizados por ProgressUi (src/ui/progress-ui.js).

4. Arquitetura #

Visão simples: um controlador por formulário (FormController, src/core/controller.js) mantém um objeto de estado reativo (exposto como $form) e um conjunto de Field (src/core/field.js), um por nome de campo. Tudo o que é variável — regras, máscaras, transportes, adaptadores de resposta e de UI — fica em um registro global (src/core/registry.js), consultado por nome.

Equivalente textual da Figura 1
  1. O Alpine processa x-form; o handler registrado por AlpineFormPlugin cria um FormController e registra controller.destroy() como cleanup.
  2. O controlador cria um Field por grupo de controles e, por campo, um RemoteValidator (se houver data-form-remote), um FileManager (campos de arquivo) e uma máscara (se o módulo estiver carregado).
  3. No envio, usa o serializador, um transporte, um adaptador de resposta e, para HTTP 202, o JobPoller.
  4. A UI é atualizada pelo adaptador de UI (padrão: DefaultUiAdapter) e por ProgressUi.
  5. Validadores, máscaras, transportes e adaptadores são buscados por nome no registro global; plugins só usam a API pública.

5. Ciclo de vida #

Carregamento e registro do plugin

src/index.js executa registerBuiltins() no carregamento do módulo: registra os validadores e normalizadores embutidos, os transportes xhr e fetch, os adaptadores de resposta default, laravel e joomla, o adaptador remoto default, o adaptador de UI default e o inspetor image. AlpineFormPlugin(Alpine) guarda a referência ao Alpine em services, registra Alpine.directive('form', …) e Alpine.magic('form', …), e agenda diagnoseUninitialized para o evento alpine:initialized.

Descoberta do formulário

Não há varredura própria do documento: o Alpine descobre o form ao processar a diretiva x-form dentro de um componente. O handler avalia a expressão (se houver), cria new FormController(el, options, { reactive: Alpine.reactive, nextTick }) e registra cleanup(() => controller.destroy()). Erros:

  • StateError (form já inicializado) → aviso no console, sem segundo controlador.
  • Outros erros (ex.: ConfigError por opção inválida no form, form aninhado) → data-form-state="config-error" no form e console.error.
  • Form fora de componente Alpine → nunca é processado; diagnoseUninitialized avisa uma vez após alpine:initialized, e AlpineForm.diagnose() devolve a lista.

Construtor

  1. Valida o elemento (HTMLFormElement, não aninhado, não inicializado).
  2. readFormConfig(form, options) aplica a precedência padrão < configure() < x-form < atributos do form; opção desconhecida em x-form é erro.
  3. Cria o estado com env.reactive(Object.assign(initialState(), publicMethods())): o mesmo objeto contém dados e métodos — é o $form.
  4. Cria o adaptador de UI (registry.get('uiAdapter', config.ui)), o ProgressUi e as extensões (registry.getFormHooks()).
  5. Registra-se em controllers, instala listeners (installListeners) e o MutationObserver (observe), e agenda initialize() no nextTick do Alpine.

Uma consequência do nextTick: diretivas Alpine filhas (x-for, x-if, :value) já foram processadas quando os campos são descobertos.

Descoberta e registro dos campos

refresh() chama discover(), que percorre form.elements (inclui controles fora da árvore com form="id") e [data-form-component]:

  • isManageable aceita INPUT, SELECT, TEXTAREA; exclui tipos de botão (SKIP_TYPES) e data-form-ignore.
  • Agrupa por name. Radios formam um grupo; checkboxes também (hiddens de mesmo nome viram companions). Outros controles com nome repetido viram campos separados com chaves nome.0, nome.1…
  • A chave é canônica: nameToKey('itens[0][nome]') = itens.0.nome; documentos[] = documentos.
  • Controle com data-form-v sem name e componente sem data-form-name geram erro de configuração.

Para cada grupo, refresh reaproveita o Field existente (via controlIndex, mapa controle → campo) ou chama createField, que cria o estado do campo em state.fields[key], chama setupField (configuração, FileManager, RemoteValidator, assinatura de componente, debouncer) e tira o snapshot inicial usado para dirty. Campos que sumiram do DOM passam por destroyField. Por fim: dependências, controles externos, UI de progresso, listas de arquivos e agregados.

Instalação de listeners

Listeners são delegados no <form>, não por input (installListeners/controlHandlers): beforeinput e input em fase de captura (máscara antes de x-model), input, change, focusout, compositionstart/end, além de submit, reset, click (cancelar, pausar, retomar, remover existente) e dragover/dragleave/drop. Cada remoção é guardada em this.cleanups. Controles associados por form="id" fora da árvore recebem listeners próprios (bindExternalControls), e contêineres [data-form-for] recebem os de clique e arrastar (bindExternalUi).

Consequência da delegação: campos adicionados depois (via x-for) já estão cobertos pelos listeners; só precisam ser descobertos pelo refresh.

6. Motor de validação #

Visão simples: o atributo data-form-v é transformado uma vez (na configuração do campo) em uma lista de regras compiladas, cada uma com seu validador já resolvido no registro e parâmetros já convertidos. Cada validação executa essa lista sobre o valor atual e produz mensagens.

Transformação passo a passo

1. HTML 
<input name="nome"
       data-form-v="required|min:3|max:120"
       data-form-msg.required="Informe seu nome."
       data-form-msg.min="Digite pelo menos :min caracteres.">
2. Localização do atributo

Field.readConfiguration() lê this.groupAttribute('data-form-v'). groupAttribute procura o atributo em todos os controles do grupo (ex.: todos os radios) e lança ConfigError se houver valores divergentes. Opções herdáveis (modo de validação, debounce…) usam resolveFieldOption: campo → ancestral mais próximo dentro do form → configuração do form.

3. Tokenização — tokenize

Percorre a string caractere a caractere; | separa regras, o primeiro : separa nome de parâmetros, , separa parâmetros; \|, \:, \, e \\ escapam. Limite de 2000 caracteres (MAX_RULES_LENGTH). Resultado (estrutura real):

[ { name: 'required', args: [], hasParams: false },
  { name: 'min',      args: ['3'], hasParams: true },
  { name: 'max',      args: ['120'], hasParams: true } ]
4. Compilação — parseRules → convertArgs → convertParam

Para cada token: valida o nome (/^[a-z][a-z0-9_]*$/), rejeita repetição, busca registry.get('validator', nome) (desconhecida → ConfigError com sugestão por distância de Levenshtein ≤ 2) e converte argumentos pelo tipo declarado no validador (integer, number como string decimal, size, field, date-or-field, enum, ratio, dimensions). Resultado por regra:

{ name: 'min', def: <definição do validador>, args: ['3'],
  params: { min: 3 }, positional: [3], refs: [] }

refs lista campos referenciados (ex.: same:senha → ['senha']) e alimenta o grafo de dependências. A combinação required + optional/nullable é rejeitada.

5. Execução — FormController.validateField
  1. Aborta a execução anterior do campo (field.abort.abort()) e incrementa field.runToken; cria novo AbortController.
  2. Atalhos: campo com erro de configuração → mensagem __config; desabilitado ou dispensado (data-form-hidden="skip" e invisível) → sem erros e validated=false; hidden sem regras → válido.
  3. Lê o valor na representação de validação (field.validationValue()) — ou o snapshot recebido.
  4. input type=number com validity.badInput → erro numeric.
  5. Regras de presença (def.presence: required, accepted, required_if…) rodam primeiro; com data-form-errors="first", para no primeiro erro.
  6. Se o valor está vazio (fieldIsEmpty) e passou na presença, termina válido: as demais regras não rodam para vazio.
  7. Regras síncronas; depois, se não houve erro, regras assíncronas (def.async) em sequência, verificando o signal.
  8. Se não houve erro e o campo tem data-form-remote, executa runRemote (capítulo 10).
  9. finish() só grava o resultado se token === field.runToken; caso contrário devolve { stale: true } e descarta.
6. Resultado da regra — runRule

O validador recebe (value, ctx) e pode devolver true/undefined/null (válido), false, uma string, ou { valid:false, variant, vars, message, items }. Promises são aguardadas. Para "ab" com min:3: o validador min devolve inválido; runRule monta vars com ruleVars ({ value: 'ab', min: 3 }) e pede a mensagem.

7. Escolha da mensagem — resolveMessage
  1. data-form-msg.<regra> do campo (aqui: "Digite pelo menos :min caracteres.");
  2. data-form-msg genérico do campo;
  3. mensagens configuradas (configure({ messages })/x-form) para regra.variante e regra — a string devolvida por um validador entra neste nível quando não há mensagem configurada;
  4. DEFAULT_MESSAGES para regra.variante e regra (ex.: min.numeric em campos numéricos);
  5. __fallback: "Confira o valor de :field."

interpolate troca :nome por vars[nome] quando a chave existe (senão mantém o texto). :field é o rótulo (data-form-label → <label> associado → name). :value é vazio para campos sensíveis (safeValuePlaceholder). Resultado: "Digite pelo menos 3 caracteres."

8. Até o DOM

finish grava state.localErrors, chama composeErrors (errors = localErrors + serverErrors; atualiza valid/invalid e $form.errors[key]), renderField (que calcula uma view com fieldView e chama ui.renderField) e dispara form:validated. O adaptador padrão cria (uma vez) um elemento .af-error após o controle, escreve com textContent, adiciona seu id a aria-describedby e define aria-invalid="true".

Regras desconhecidas e configuração inválida

Qualquer ConfigError em Field.configure() é guardado em field.configError: o campo passa a mostrar a mensagem __config ("Este campo tem uma configuração inválida e não pode ser validado."), o erro técnico vai para o console e para $form.configErrors, e o envio é bloqueado (runSubmit falha com config se houver erros de configuração). Consequência: um erro de digitação em data-form-v não passa despercebido em produção. Testado em tests/unit/validation.test.js › regra desconhecida bloqueia o campo e o envio.

Limitação

Mensagens por variante no próprio campo (ex.: data-form-msg.min.numeric) não são consultadas: o nível 1 usa apenas fieldMessages[regra]. Variantes só são resolvidas nas mensagens configuradas e nas padrão.

Linha do tempo (modo padrão live)

  1. Página carregada. initialize → refresh. Valores iniciais são lidos, máscaras formatam o valor inicial sem marcar dirty (o snapshot é tirado depois). Nenhum erro é exibido.
  2. Usuário entra no campo e digita. input → onInput → handleValueChange('input'): sincroniza o valor e dirty, limpa erros do servidor do campo (clear-on-change), dispara form:change. Como o campo ainda não foi tocado nem validado, não valida.
  3. Sai do campo. focusout → onBlur: touched = true, cancela o debounce e valida imediatamente (trigger: 'blur'). Erro aparece.
  4. Corrige. Cada input chama field.debouncer(); a validação roda 200 ms (ou data-form-debounce) após a última tecla e o erro some.
  5. Envia. runSubmit → validateForSubmit valida todos os campos de uma vez (Promise.all, sem debounce de remota), com política de snapshot (abaixo).

Outros modos: input (valida desde a primeira tecla, com debounce), blur, change e submit; nos modos blur/submit, um campo já validado volta a ser revalidado ao digitar. Radios, checkboxes e selects validam no change em live.

Composição IME

Durante composição (teclados de idiomas asiáticos, acentuação composta), compositionstart marca field.composing = true; onInput e onMaskInput ignoram eventos com isComposing. Em compositionend, a máscara formata e o valor é tratado como um input. Testado em validation.test.js e masks-integration.test.js (IME).

Controle de concorrência e respostas antigas

Três mecanismos, todos implementados:

  1. runToken por campo: cada validação incrementa o contador; só o resultado da execução mais recente é aplicado (finish compara o token).
  2. AbortController por campo: uma nova validação aborta a anterior; regras assíncronas e a consulta remota recebem o signal; aborto não vira erro.
  3. Comparação de valor na remota: após a resposta, runRemote descarta o resultado se field.validationValue() não for mais o valor consultado.

No envio, validateForSubmit tira um snapshot (valueSnapshot: JSON.stringify(field.comparableValue()) por campo) antes e depois da validação completa; se algo mudou durante validações assíncronas, valida de novo (até 3 tentativas); persistindo, falha com changed ("Os dados foram alterados durante a validação. Revise e envie novamente."). Depois da resposta, erros do servidor de campos cujo valor mudou desde o envio são descartados (applyServerErrors com snapshot).

O envio duplicado é impedido em submit(): enquanto this.submission existir, a mesma Promise é devolvida.

8. Atualização da UI #

Duas camadas convivem:

  • Reativa (Alpine): qualquer expressão sua que leia $form (ex.: :disabled="$form.submitting", x-text="$form.firstError('email')").
  • Imperativa (adaptador de UI): o controlador chama ui.renderField(field, view), ui.renderSummary(view), ui.renderFileList(…); a view é calculada por FormController.fieldView.

A view de um campo

fieldView devolve { status, messages, info, showValid }, com status em idle · pending · invalid · valid:

  • erro de configuração → invalid com a mensagem __config;
  • remota pendente sem erro local → pending e info "Verificando...";
  • há erros e (campo validado ou há erro do servidor) → invalid. Consequência: erros nunca aparecem em campos que o usuário ainda não "atingiu", a menos que venham do servidor;
  • validado e não validando → valid (classe af-valid só com data-form-show-valid).

O adaptador padrão (DefaultUiAdapter)

  • Cria o elemento de erro .af-error logo após o controle (ou usa data-form-error-target), marcado com data-form-generated="error" e id único por formulário.
  • Mensagens via textContent: HTML vindo do servidor não é interpretado.
  • Adiciona o id ao aria-describedby preservando valores existentes, define aria-invalid, e guarda os valores originais para restaurá-los no destroy.
  • Classes: af-invalid, af-valid, af-pending… (DEFAULT_CLASSES); o plugin Bootstrap troca por is-invalid/invalid-feedback estendendo a mesma classe.
  • Resumo (renderSummary): com data-form-summary="general" (padrão) lista apenas erros sem campo visível (erros gerais, hiddens sem destino); com all, todos, com botões que focam o campo. Recebe role="alert" e tabindex="-1".
  • Lista de arquivos (renderFileList): <ul data-form-generated="file-list"> com nome, tamanho, erros por arquivo, thumbnail (quando houver) e botão "Remover" com aria-label. O foco é devolvido ao botão equivalente após re-renderizar.

Progresso e status (ProgressUi)

setPhase e as atualizações de progresso chamam renderProgress, que calcula state.status (statusText, a partir das mensagens status.*) e chama ProgressUi.render: preenche [data-form-status], [data-form-progress-percent|loaded|total|speed|eta|elapsed], atualiza a barra e habilita/desabilita [data-form-cancel], [data-form-pause] e [data-form-resume] conforme a fase. disabled só é escrito quando muda (setDisabled), para não gerar mutações de DOM desnecessárias.

9. Dependências entre campos #

Exemplo: senha_confirmacao com data-form-v="required|same:senha". Quando senha muda, a confirmação precisa ser revalidada.

  1. Declaração: parâmetros do tipo field e date-or-field que referenciam outro campo entram em rule.refs; field.refs é a união. Campos de data-form-remote-fields também contam.
  2. Grafo: rebuildDependencies (em todo refresh) monta dependents: campo referenciado → conjunto de campos que dependem dele.
  3. Propagação: após cada mudança de valor, handleValueChange chama propagate(field), que revalida os dependentes já validados, tocados ou após uma tentativa de envio, invalidando antes o cache remoto deles.
  4. Leitura do outro valor: o validador usa ctx.other(ref) (otherInfo), que devolve o valor na representação de validação (ou null se desabilitado) e lança ConfigError se o campo não existir.

Ciclos (ex.: a same:b e b same:a) são permitidos: a propagação é de um nível — validateField de um dependente não chama propagate — então não há laço. diagnostics().cycles lista os ciclos encontrados (dependencyCycles). Testado em validation.test.js › ciclos são detectados sem laço infinito.

Limitação

A propagação é de um único nível: se C depende de B e B depende de A, mudar A revalida B, mas não C (C só é revalidado quando B mudar de valor).

10. Validação remota #

Visão simples: depois que as regras locais passam, o valor é consultado no servidor. Exemplo real (examples/cadastro.php):

<input name="email" type="email" data-form-v="required|email"
       data-form-remote="/api/validar-email" data-form-remote-method="post" data-form-remote-debounce="500"
       data-form-msg.remote="Este e-mail já está cadastrado." data-form-msg.pending="Verificando...">

Requisição

RemoteValidator.buildRequest envia <param>=valor (padrão: o name do campo; data-form-remote-param muda), _field=<name> e os campos de data-form-remote-fields. POST usa application/x-www-form-urlencoded; GET coloca na query string. Cabeçalhos CSRF só para a mesma origem. Contrato esperado: { "valid": boolean, "message"?: string } (aceita mensagem); outro formato via data-form-remote-adapter.

Erros e reação

  • Rede, timeout (padrão 8 s), HTTP fora de 2xx, resposta não-JSON ou fora do contrato → inconclusivo. Rede/timeout e status 408/425/429/5xx são repetidos (retries, padrão 1) com backoff; Retry-After é respeitado até 10 s.
  • Política allow (padrão): o campo fica sem erro e com info "Não foi possível verificar agora. O valor será conferido no envio."; block: erro "Não foi possível verificar este valor agora.".
  • Aborto (novo valor digitado, destroy) → resultado descartado, sem erro.
  • Somente resultados valid: true/false entram no cache (inconclusivo não é memorizado). $form.clearRemoteCache(nome) limpa; erros do servidor no envio invalidam a entrada do valor atual.
Segurança

GET em campo sensível (type="password" ou data-form-sensitive) sem data-form-remote-allow-query é erro de configuração: o valor iria para a URL, logs e histórico.

Limitação

A consulta remota usa credentials: 'same-origin' fixo (RemoteValidator.validate), independentemente de data-form-credentials; consultas a outra origem não enviam cookies.

11. Máscaras e representações de valor #

Máscara formata a digitação; validação decide se o valor é aceitável. São mecanismos separados: 529.982.247-24 tem formato de CPF perfeito e dígito verificador errado — só a regra cpf detecta. Por isso a máscara nunca substitui data-form-v.

O módulo é opcional (alpine-form-masks), sem dependência externa: motores próprios em src/masks/pattern-engine.js (padrões) e src/masks/numeric-engine.js (inteiro, decimal, moeda, percentual). Sem o módulo, data-form-mask é erro de configuração.

As cinco representações

exibido (display)
O texto no input.
bruto (raw)
Só os caracteres significativos, sem literais. Na moeda: sinal + dígitos digitados — não é um número.
formatado (formatted)
Resultado da formatação do valor atual.
canônico (canonical)
Forma estável para máquinas: documentos = bruto; datas = ISO quando a data existe; números = string decimal com ponto e escala fixa (nunca Number). Normalizadores (data-form-normalize) são aplicados aqui.
validado / enviado
Uma das anteriores, escolhida por data-form-mask-validation-value e data-form-submit-value (padrões definidos por máscara). Field.validationValue() e Field.submitValue() leem Field.representations()[…].

Observações: os padrões de validação/envio variam por máscara (no CEP do exemplo, valida o raw e envia o formatado; no padrão personalizado, valida e envia o formatado). A data inexistente não ganha forma canônica ISO e é recusada pela regra date. Sem data-form-mask-negative, o sinal é descartado.

Moeda: quatro etapas distintas

  1. Apresentação localizada: prefixo/sufixo, separadores de milhar e decimal vêm de Intl.NumberFormat(locale, { style: 'currency', currency }) (localeSymbols); agrupamento sempre de 3 em 3.
  2. Remoção de caracteres: separador de milhar digitado é ignorado; só dígitos, o separador decimal do locale e, se permitido, - são considerados.
  3. Conversão canônica: string com ponto decimal, zeros à esquerda removidos (0071 → 71). Em colagem sem o separador do locale, 1234.56 é lido como decimal; com exatamente 3 dígitos após o ponto, é milhar.
  4. Precisão: casas além da escala são descartadas, não arredondadas; no blur, com pad, completa as casas (R$ 1.234,5 → R$ 1.234,50). A regra min_value:0.01 compara strings decimais (compareDecimal), sem ponto flutuante.

Integração e listeners

Field.readConfiguration recusa máscara fora de text/tel/search/textarea e chama provider.attach(field, nome) → attachMask (src/masks/runtime.js), que obtém a fábrica no registro, lê a configuração (data-form-mask-*), adiciona inputmode/placeholder se ausentes e formata o valor inicial. Os eventos chegam pelos listeners delegados do controlador, em fase de captura, antes de x-model:

  • beforeinput → handleBeforeInput: marca colagem; para Backspace/Delete com cursor colapsado ao lado de um literal, remove o caractere significativo vizinho (deleteAcrossLiteral), reformata e reposiciona o cursor — evita o usuário "preso" atrás de um separador que seria reinserido.
  • input → handleInput: reformata a partir do valor atual e do cursor (mask.format(valor, cursor, { paste })).
  • change → reformata; focusout → onBlur da máscara (ex.: completar casas decimais).

Cursor, seleção, colagem e exclusão

No motor de padrões, o cursor é mapeado contando quantos caracteres significativos existiam antes dele na entrada e posicionando-o após o mesmo número de tokens na saída (formatWithCaret). Seleção substituída por digitação, colagem formatada ou bruta e edição no meio são tratadas por essa mesma regra. O cursor só é restaurado se o input estiver focado.

Limitação

Desfazer/refazer (Ctrl+Z) usa a pilha do navegador; como o valor é reescrito por script, pode pular estados intermediários (comentário de attachMask). Nenhum suporte próprio a undo é implementado.

Troca de máscara, valores iniciais, API, reset, serialização e destroy

  • Troca dinâmica (:data-form-mask): o atributo é observado; reconfigureField destrói a máscara anterior e reformata a partir dos caracteres significativos.
  • Valor inicial: formatado no attachMask, antes do snapshot — não marca dirty.
  • setValue(nome, valor, { as }): com máscara, mask.fromValue; as: 'canonical' usa a conversão inversa (ex.: '1234.5' → R$ 1.234,50, raw 123450 — verificado no Chrome). getValue(nome, { as }) aceita display, raw, formatted, canonical, validation, submit.
  • Reset: após o reset nativo restaurar o atributo value, afterReset reformata.
  • Serialização: collectEntries substitui o valor do controle pela representação de envio. Nenhum input hidden é criado.
  • Destroy: remove inputmode/placeholder que a máscara adicionou.

12. Arquivos e previews #

Problema: input.files é somente leitura em vários cenários, então "remover um arquivo da lista" não pode depender dele. Solução observável: cada campo de arquivo tem um FileManager (src/files/file-manager.js) cuja lista interna (items) é a fonte de verdade do envio.

  • Entrada: change → fromInput(); arrastar-e-soltar em [data-form-dropzone] e $form.addFiles → add(). Com data-form-files-append, novas seleções somam; sem ele, substituem.
  • Duplicados: impressão digital nome + tamanho + lastModified; ignore (padrão) ou allow.
  • Remoção: remove(id) libera o item; syncInput tenta reescrever input.files com DataTransfer e, se o navegador recusar, apenas limpa o input quando a lista fica vazia — o envio continua correto porque collectEntries lê field.files.newItems().
  • Regras: por arquivo (file_max, ext, mime, image, dimensões…) com erro no item da lista, e por grupo (files_max, files_total_max). Dimensões vêm do inspetor image (inspectImage), memorizado por item.
  • Preview: object URL só para imagens raster de até 20 MB (previewFor); SVG nunca (pode conter script). Revogado em releaseItem (remover, limpar, reset, destroy).
  • Existentes (edição): elementos [data-form-existing] com data-form-existing-id; "remover" marca para exclusão e o id é enviado no campo data-form-existing-remove-name; regras de quantidade contam existentes mantidos + novos.
  • Campo vazio: sem seleção, uma parte de arquivo vazia é enviada, como o navegador faria (o PHP recebe UPLOAD_ERR_NO_FILE).
Segurança

Extensão, MIME e até a assinatura lida no navegador podem ser forjados. O backend de referência inspeciona o conteúdo real (server/src/UploadInspector.php) e saneia nomes; aplicações integradoras devem fazer o mesmo.

13. Serialização #

collectEntries(controller, { submitter, replacements }) (src/core/serializer.js) reproduz o algoritmo de "lista de entradas" do HTML sobre form.elements:

  • ordem da árvore, incluindo controles associados por form="id";
  • ignora desabilitados, sem name, checkbox/radio desmarcados e botões que não originaram o envio (o submitter entra com seu name/value);
  • nomes repetidos geram entradas repetidas (nunca colapsadas); select multiple gera uma entrada por opção selecionada; dirname é respeitado.

Diferenças intencionais: campos de texto usam a representação de envio (field.getValue('submit')); arquivos vêm da lista interna (ou de replacements, usado pelo módulo de chunks para trocar arquivo por token); checkbox com data-form-unchecked-value envia esse valor quando desmarcado; componentes externos entram no final.

Codificação (buildRequestBody): GET → query string; multipart → FormData (sem definir Content-Type, para o navegador incluir o boundary); urlencoded → URLSearchParams; json → toJsonObject.

JSON aninhado

itens[0][nome]=A, itens[0][qtd]=2, tags[]=x, tags[]=y
→ { "itens": [ { "nome": "A", "qtd": "2" } ], "tags": ["x", "y"] }    (data-form-nesting="brackets")

dots também divide por ponto; flat não aninha (repetidos viram lista). O objeto raiz é criado com Object.create(null) e segmentos __proto__, prototype e constructor lançam SerializationError. Arquivo em JSON é erro, salvo data-form-json-files="metadata" (envia {name,size,type}). Conflito de estrutura (o mesmo caminho como valor e como objeto) é erro explícito.

14. Transporte HTTP e sequência de envio #

Equivalente textual da Figura 4

idle → validating → (inválido: idle) → uploading (com chunks pode alternar com paused) → awaiting → success | error; um 202 com job leva de awaiting a processing → success | error. De validating, uploading, paused, awaiting ou processing, cancel() leva a canceled.

Sequência completa (submit → runSubmit)

  1. Interceptação: onSubmit chama preventDefault() e submit({ submitter: event.submitter }). Se já houver envio, devolve a mesma Promise.
  2. Preparação: submitted = true, submitCount++, limpa error/result/job/progress; dispara form:before-submit (cancelável) e o hook beforeSubmit (devolver false cancela).
  3. Alvo: resolveTarget: formaction/formmethod/formenctype do submitter > data-form-endpoint/data-form-method > action/method/enctype. formnovalidate pula a validação.
  4. Validação: limpa erros do servidor, fase validating, validateForSubmit. Inválido → fase idle, resumo, foco no primeiro erro, retorno { ok:false, reason:'invalid' }. Erros de configuração bloqueiam com config.
  5. Extensões: snapshot de valores e da ordem dos arquivos; beforeSend(ctx) de cada extensão (o módulo de chunks envia os arquivos aqui e preenche ctx.replacements).
  6. Montagem: collectEntries → buildRequestBody. Cabeçalhos: Accept, X-Requested-With: XMLHttpRequest, config.headers, CSRF (mesma origem), Idempotency-Key (se habilitado). SerializationError → falha serialization.
  7. Último veto: form:submit (cancelável, com url/método/cabeçalhos) e hook beforeRequest(request).
  8. Envio: tracker.start(), fase uploading, transportFor('submit')(request).
  9. Resposta: se a fase ainda era uploading, passa por onUploadComplete; o adaptador de resposta normaliza (registry.get('responseAdapter', nome)); hook afterResponse; handleResult.
  10. Resultado: 202 com job → runJob; ok → succeed (fase success, form:success, reset/redirect opcionais); senão erros aplicados aos campos e failSubmit (fase error, form:error, foco).
  11. Limpeza: o finally de submit zera this.submission; listeners de abort são removidos nos transportes.

15. Progresso #

ProgressTracker (src/transport/progress.js) usa somente eventos reais do transporte; nenhum timer simula avanço. Fórmulas exatamente como implementadas:

percent    = floor(loaded / total × 100)                      só se lengthComputable e total > 0; senão null (indeterminado)
velocidade = (loaded_último − loaded_primeiro) / (t_último − t_primeiro) × 1000   [bytes/s]
             amostras dos últimos 3 s (janela deslizante); exige ≥ 500 ms entre a primeira e a última amostra
ETA        = round((total − loaded) / velocidade)             [s]; só com total conhecido, velocidade > 0,
             ≥ 1 s decorrido e antes do fim do upload
elapsed    = (instante do fim do upload ou agora) − início    [ms]

Não há suavização exponencial: a "suavização" é a própria janela de 3 s (amostras mais antigas são descartadas, mantendo ao menos 2). Ao marcar o upload como concluído (markUploaded), loaded passa a total, velocidade e ETA ficam null.

loaded / total
Bytes do corpo HTTP transmitido (inclui boundaries e cabeçalhos das partes do multipart) — por isso total de um arquivo de 8 MiB é ligeiramente maior que 8 MiB (verificado em tests/e2e/uploads.spec.js).
lengthComputable
Vem do evento do navegador; falso → indeterminate: true, percent: null.
uploaded
O corpo terminou de sair.

Por que 100% não é sucesso

100% significa que o navegador terminou de transmitir o corpo. O servidor ainda vai validar, gravar e responder — e pode recusar. Por isso existem fases distintas:

  1. Transmissão — uploading: barra com bytes reais.
  2. Espera da resposta — awaiting: "Envio concluído. Aguardando resposta do servidor…".
  3. Processamento no servidor — processing (só com 202 + job): percentual apenas se o backend informar.
  4. Conclusão — success, somente quando a resposta (ou o job) confirma.

Se a conexão cair na fase 2, o resultado é unknown: a operação pode ter sido concluída no servidor.

16. Arquivos grandes: chunks e retomada #

Implementado no módulo opcional alpine-form-chunks (src/chunks/chunk-upload.js: ChunkUpload; src/chunks/index.js: ChunkExtension) com backend funcional em server/src/ChunkStore.php. Exemplo executável: examples/chunks.php.

Fluxo no cliente

  1. ChunkExtension.beforeSend cria (ou reaproveita) um ChunkUpload por arquivo novo de cada campo com data-form-chunked, coloca o formulário na fase uploading e inicia todos em paralelo.
  2. start(): calcula a impressão digital rápida (quickFingerprint: nome, tamanho, data e hash de amostras do início e do fim); com -persist, procura sessão salva para o mesmo arquivo; senão createSession (uploadId).
  3. runParts: fila das partes não confirmadas; até concurrency (padrão 3, máx. 6) workers. Cada parte: Blob.slice(início, fim), SHA-256 (crypto.subtle, se disponível) e PUT.
  4. Retry (uploadPart): 408/429/5xx e rede/timeout são repetidos até retries (padrão 5) com backoffDelay (exponencial com jitter: min(máx, base·2^tentativa) sorteado entre metade e o teto) ou Retry-After; 409 falha imediatamente; 404/410 recria a sessão uma vez.
  5. complete() envia o manifesto e recebe o token; o ID persistido é apagado.
  6. O controlador serializa o formulário com replacements: o campo de arquivo leva o token, não os bytes.

Progresso sem dupla contagem

loaded(arquivo) = Σ tamanho das partes CONFIRMADAS + Σ bytes em voo das partes ainda não confirmadas
loaded(form)    = Σ loaded(arquivo);  total = Σ tamanho dos arquivos (bytes úteis, sem multipart)

Quando uma parte é repetida, sua entrada em inflight recomeça de zero; quando é confirmada, sai de inflight e entra em received. Testado em tests/unit/chunks.test.js › retry com backoff em 503 sem dupla contagem.

Pausa e retomada

pause() cria uma "porteira" (pauseGate), aborta as partes em voo (seus bytes deixam de contar) e muda o status para paused; os workers esperam a porteira antes de pegar a próxima parte, e uma parte que ainda calculava o hash quando a pausa chegou não é enviada. resume() consulta o servidor (syncStatus: GET) para saber quais partes já foram confirmadas e libera os workers. Botões: [data-form-pause], [data-form-resume]; API: $form.pauseUpload(), $form.resumeUpload(), $form.getUploadSession().

Retomada após recarregar a página

Com data-form-chunk-persist, somente metadados (uploadId, nome, tamanho, lastModified, chunkSize, data) vão para o localStorage. O navegador não mantém acesso ao arquivo após o reload: o usuário precisa selecionar o mesmo arquivo de novo; ao enviar, a impressão digital é comparada e só as partes faltantes são enviadas. $form.uploads[campo].resumable lista sessões salvas para exibir um aviso.

Quatro níveis diferentes de "pronto"

  1. Bytes enviados — saíram do navegador (contam em inflight).
  2. Partes confirmadas — o servidor respondeu 200 e gravou a parte atomicamente.
  3. Arquivo montado — complete verificou o manifesto e montou file.bin; existe um token.
  4. Operação persistida — o endpoint do formulário vinculou o token (ChunkStore::bind) e gravou o registro de negócio.

Integridade, limpeza e limites

  • SHA-256 por parte (X-Chunk-Sha256) verificado pelo servidor; manifesto final = SHA-256 da concatenação binária dos hashes das partes (manifestOf no cliente, ChunkStore::manifest no servidor), comparado em complete; se alguma parte ficou sem hash, o manifesto não é enviado. Requer contexto seguro (HTTPS ou localhost); sem crypto.subtle, as partes vão sem hash.
  • Cancelar envia DELETE da sessão (discard, melhor esforço); sessões abandonadas expiram e são removidas por php server/bin/cleanup.php (deve ser agendado).
  • Tamanho de parte entre 64 KiB e 100 MiB (readChunkConfig).

17. Processamento posterior (jobs) #

Quando a resposta é 202 com job (jobFrom em response.js aceita job.id, job_id, jobId, status_url, cancel_url), runJob coloca o form em processing e cria um JobPoller (src/jobs/poller.js):

  • Sem sobreposição: a próxima consulta só é agendada depois que a anterior termina (run é um laço com await sleep + await poll).
  • Intervalo: começa em data-form-job-interval (1,5 s); se nada mudou, multiplica por 1,5 até data-form-job-max-interval (10 s); se mudou, volta ao inicial; Retry-After tem prioridade.
  • Falhas de rede: até 5 consecutivas são toleradas com backoff; 404/410 → job-missing; status fora de queued|processing|succeeded|failed|canceled → job-contract.
  • Tempo total: data-form-job-timeout (10 min) → job-timeout ("O processamento está demorando mais que o esperado…"); o id persistido é mantido para retomar depois.
  • Progresso: só aparece se o backend enviar progress entre 0 e 100. No backend de referência, o worker informa a fração de bytes lidos do CSV.
  • Cancelar: cancel()/[data-form-cancel] encerra apenas a observação ("Acompanhamento encerrado. O processamento pode continuar no servidor."); $form.cancelJob() envia DELETE ao cancel_url.
  • Persistência: com data-form-job-persist, { id, statusUrl } fica no sessionStorage e initialize → resumePersistedJob retoma o acompanhamento após recarregar.

O backend de referência usa uma fila em arquivos (server/src/JobQueue.php) e um worker real (php server/bin/worker.php). Sem o worker, o job fica em queued.

Associação de erros a campos (applyServerErrors → resolveErrorTarget)

  1. normalizeErrors aceita string ou lista por chave; chaves "", _, _general, * são gerais.
  2. normalizeErrorKey: chaves com colchetes são convertidas para a forma com ponto (itens[0][nome] → itens.0.nome; jform[title] → jform.title).
  3. Procura o campo pela chave canônica ou pelo nome original.
  4. Sem campo direto e chave terminando em .N: se o pai é campo de arquivo, o erro vai para o N-ésimo arquivo enviado (usando a ordem gravada no snapshot); se o pai é grupo de checkboxes ou select múltiplo, vai para o grupo.
  5. Sem correspondência → generalErrors → resumo. Nada é descartado em silêncio.
  6. Campo cujo valor mudou desde o envio: o erro é descartado (não se aplica resposta antiga a valor novo).

Campos repetidos com o mesmo nome (sem colchetes) recebem chaves nome.0, nome.1…, então um erro nome.1 chega ao segundo. Nomes com ponto literal fora de colchetes (ex.: usuario.email) já são chaves com ponto e casam diretamente.

Limpeza após edição

Com data-form-server-errors="clear-on-change" (padrão), handleValueChange limpa serverErrors do campo na primeira mudança. Com keep, permanecem até o próximo envio (todo envio começa com clearServerErrors).

request_id

19. DOM dinâmico #

Campos adicionados por x-for, removidos por x-if, regras trocadas por :data-form-v: um MutationObserver por formulário (observe/onMutations) observa childList e um conjunto fixo de atributos (OBSERVED_ATTRIBUTES: name, disabled, type, multiple, form, data-form-v, data-form-mask, data-form-remote, data-form-hidden, data-form-submit-value…).

  • Mutação relevante = nó adicionado/removido que é ou contém controle, componente, existente, lista de arquivos, progresso ou status; ou mudança de atributo observado em um controle.
  • Conteúdo gerado pela própria biblioteca ([data-form-generated]) e atributos em <button> são ignorados. Sem esse filtro, a UI gerada provocaria um ciclo de re-renderização — o defeito existiu e foi corrigido nesta versão, com teste de regressão (dynamic.test.js › UI gerada não dispara refresh em ciclo) e verificação de DOM estável em todas as páginas de exemplo (E2E).
  • Mutações são agrupadas: um único refresh() por tarefa (setTimeout(…, 0)).
  • refresh reaproveita campos cujos controles continuam no DOM (estado preservado), reconfigura os que tiveram atributos alterados (reconfigureField, revalidando se já estavam validados), troca a chave quando o nome muda (rekeyField, ex.: reindexação de linhas) e destrói os que sumiram (destroyField).
  • Ocultos: com data-form-hidden="skip", um campo invisível (x-show) é dispensado da validação; com o padrão validate, continua validado.
  • Campos fora do form: controles com form="id" são incluídos; elementos em [data-form-for="id"] recebem $form e UI. Para controles externos adicionados depois, chame $form.refresh() (o observador só observa a árvore do form).

20. Reset, cancelamento e destroy #

Cancelamento (cancel())

Aborta o AbortController da submissão (o transporte chama xhr.abort() ou aborta o fetch), para o poller (só a observação) e pede às extensões que cancelem (chunks descarta as sessões com DELETE). O envio termina com fase canceled e evento form:cancel — não é tratado como erro de preenchimento.

Reset

$form.reset() dispara form:reset (cancelável), cancela o que estiver em andamento, chama o reset nativo do form (valores voltam aos atributos value/checked/selected) e afterReset: por campo, cancela debounce e validação, limpa arquivos (revogando previews), reformata a máscara, zera touched/validated/validating/erros/remote; no form, zera erros gerais, submitted, result, job, progresso e volta a idle. O botão type="reset" segue o mesmo caminho (onNativeReset).

Destroy

Chamado pelo cleanup do Alpine quando o form sai do DOM, ou por $form.destroy():

  1. cancel(); marca destroyed; cancela o refresh pendente; desconecta o MutationObserver.
  2. Remove todos os listeners (cleanups, externos de controles e de [data-form-for]).
  3. Por campo: cancela assinatura de componente, debounce, validação em voo; destrói máscara; destrói o FileManager (revoga object URLs); ui.removeField remove elementos de erro criados e restaura aria-describedby/aria-invalid originais.
  4. Destrói extensões, o adaptador de UI (remove o resumo criado) e o ProgressUi; remove aria-busy e data-form-state; remove o form de controllers e limpa os campos.

Testado em submit.test.js › destroy remove listeners, elementos gerados e atributos ARIA; remover o form do DOM destrói o controlador.

25. Configurações #

Global

AlpineForm.configure({ … }) aceita qualquer chave de OPTION_SPECS (as do form) e as extras: headers, csrf ({ meta: 'csrf-token', header: 'X-CSRF-TOKEN' } ou null), messages, locale (pt-BR), remote ({ debounce: 400, timeout: 8000, cache: 20, cacheTtl: 60000, method: 'post', inconclusive: 'allow', retries: 1 }), files ({ duplicates: 'ignore', preview: true, append: false, previewMaxBytes: 20 MB }), patternMaxLength (500), patternMaxInput (2000), hooks, clock. Chave desconhecida é erro.

Formulário

Objeto em x-form="{ … }" (mesmas chaves; objetos como remote são mesclados) e atributos data-form-* no form, que têm prioridade.

Campo

Atributos no controle (e, para opções herdáveis, em ancestrais dentro do form). Lidos por Field.readConfiguration; divergências entre controles de um grupo são erro.

Adaptador

Adaptadores recebem sua configuração na fábrica: UI ({ form, uid, controller }), máscara (config lida de data-form-mask-*), transporte (o objeto request).

Responsabilidades da aplicação integradora

  • Revalidar todos os campos; autorizar cada operação (o backend de referência responde 404 a recursos de outro dono).
  • Verificar o conteúdo real dos arquivos (assinatura, decodificação), limitar tamanho, sanear nomes e armazenar fora da raiz pública.

29. Acessibilidade #

Implementado

  • ARIA nos campos: aria-invalid="true" e aria-describedby apontando para a mensagem, preservando valores existentes e restaurando-os no destroy.
  • Mensagens: os elementos de erro não são live regions (evita anúncios a cada tecla); são lidos ao focar o campo. O resumo recebe role="alert" e tabindex="-1".
  • Foco: no envio inválido, foco no primeiro campo com erro na ordem do documento (radios: o marcado ou o primeiro), após form:reveal/hook reveal; sem campo focável, foco no resumo. Rolagem suave respeita prefers-reduced-motion.
  • Estado de envio: aria-busy="true" no form durante fases ativas; [data-form-status] recebe role="status" e aria-live="polite" (se ainda não tiver), então a mudança de fase é anunciada; os valores originais são restaurados no destroy.
  • Teclado: listas de arquivos com botões reais e aria-label "Remover <arquivo>"; o foco volta ao item equivalente após re-render ou ao input quando a lista esvazia. A dropzone é complementar: o input de arquivo continua acessível.
  • Máscaras: inputmode adequado (numérico, telefone, decimal) sem trocar o type.

Responsabilidades do integrador

  • Usar <label for> (também alimenta :field), <fieldset>/<legend> em grupos e contraste adequado nas classes af-*.
  • Garantir que barras de progresso tenham nome acessível (aria-label).
  • Testar com leitores de tela: não há testes automatizados com leitores de tela neste projeto.

30. Performance #

  • Listeners: delegados no form (número constante, independente da quantidade de campos).
  • DOM dinâmico: um MutationObserver por form, com filtro de atributos, e um refresh por tarefa. Cada refresh percorre todos os controles do form (custo linear no número de campos).
  • Validação: regras compiladas uma vez; debounce na digitação; remota com debounce, cache LRU (20 itens, 60 s) e cancelamento; no envio, campos validados em paralelo.
  • Arquivos: previews só quando há lista visível, até 20 MB e só raster; decodificação de imagem e inspeções memorizadas por arquivo; CSV inspecionado por amostra; chunks lidos com Blob.slice (sem carregar o arquivo inteiro), concorrência limitada.
  • Memória: object URLs revogados; listeners removidos no destroy; caches limitados.
  • Renderização: a lista de arquivos é reconstruída por inteiro a cada mudança (custo linear no número de arquivos); disabled dos botões só é escrito quando muda.
  • Tamanho (medido pelo build em dist/sizes.json): núcleo 143,8 KiB minificado / 44,9 KiB gzip; máscaras 21,7 / 7,8; chunks 19,5 / 6,7; inspetores 9,1 / 3,7; Bootstrap 1,6 / 0,8. O controlador sozinho ocupa ~48 KiB minificados.

31. Compatibilidade #

  • Alpine: peerDependency ^3.10.0; testado com 3.14.9. Usa apenas Alpine.directive, Alpine.magic, Alpine.reactive, Alpine.nextTick e o cleanup da diretiva.
  • Navegadores-alvo do build (build.mjs): ES2020, Chrome 92, Firefox 90, Safari 15, Edge 92. Os testes E2E rodam apenas no Google Chrome instalado; Firefox e Safari não são verificados automaticamente.
  • APIs com degradação: sem DataTransfer gravável, input.files não é reescrito (envio continua correto); sem crypto.subtle (contexto inseguro), chunks vão sem hash; sem MutationObserver, campos dinâmicos exigem $form.refresh().

Apresentação de 30 segundos

"O AlpineForm é um micro-framework de formulários sobre Alpine.js. Você declara regras, mensagens e máscaras nos próprios inputs; ele valida enquanto a pessoa digita, envia com progresso real, entende respostas de Laravel e Joomla, coloca cada erro no campo certo e lida com arquivos grandes em partes com pausa e retomada. Apresentação de 3 minutos

  1. Problema (30 s): formulários repetem validação ao vivo, regras entre campos, máscaras, uploads e tratamento de erros; cada tela reimplementa tudo.
  2. Ideia (30 s): o HTML declara o comportamento (data-form-v, data-form-mask…); um controlador por form executa. Erros de configuração são explícitos.
  3. Demonstração (60 s): examples/cadastro.php (erro após blur, CPF formatado e enviado sem máscara, e-mail já cadastrado) e examples/chunks.php (pausar, retomar, token).

Perguntas frequentes

Preciso registrar cada campo em JavaScript?
Não. Os campos são descobertos a partir de form.elements; o JavaScript só é necessário para extensões.
Funciona sem os módulos opcionais?
Sim. Sem eles, os atributos correspondentes são erro de configuração.
Posso usar com Bootstrap?
Sim, com alpine-form-bootstrap (data-form-ui="bootstrap"), que troca as classes do adaptador padrão.
Como sei que um formulário não foi inicializado?
AlpineForm.diagnose() e o aviso no console após alpine:initialized.

Perguntas difíceis e respostas fundamentadas

Por que Alpine?
Observação: a biblioteca usa do Alpine apenas o ciclo de vida da diretiva (criação e cleanup), a reatividade do estado e a mágica $form. Uma consequência é que a página continua sendo HTML renderizado no servidor, com comportamento acrescentado por atributos, e o estado do formulário fica disponível para expressões Alpine sem código adicional. Sem o Alpine, AlpineForm.attach funciona, mas o estado não é reativo.
Por que atributos no HTML?
O comportamento fica ao lado do elemento que ele afeta, inclusive em HTML gerado pelo servidor (Blade, templates Joomla). O custo é que erros de digitação seriam silenciosos — por isso todo atributo e regra desconhecidos são erro de configuração.
Por que não validar apenas no backend?
A validação do backend continua obrigatória. A do cliente dá retorno imediato, evita requisições inválidas e guia o foco; as duas usam as mesmas regras declaradas em lugares diferentes.
Por que máscara não é validação?
A máscara só garante formato durante a digitação; 529.982.247-24 está bem formatado e é inválido. Além disso, o valor validado e o enviado podem ser representações diferentes (raw, canônico).
Como evita respostas antigas?
runToken por campo, AbortController por validação, comparação do valor consultado na remota, snapshot no envio e descarte de erros do servidor para campos alterados desde o envio. Ver cap. 7.
Por que upload 100% não significa concluído?
100% mede bytes transmitidos; o servidor ainda pode recusar, falhar ou demorar. A fase awaiting existe para isso; com 202, ainda há processing.
Como funciona o cancelamento?
Um AbortController por envio; o transporte aborta o XHR/fetch; o poller para (só a observação); chunks descartam sessões com DELETE. Resultado: fase canceled, não erro.
O que acontece ao remover um campo?
O MutationObserver agenda um refresh; destroyField cancela validação e debounce, destrói máscara e arquivos, remove o erro do DOM, limpa estado e dispara form:field-removed. O campo sai da validação e do envio.
Como estender sem modificar o núcleo?
Registros por nome (validadores, máscaras, transportes, adaptadores, componentes) e formHook para comportamento por formulário — o módulo de chunks inteiro é implementado assim.
Quais são os pontos fracos atuais?
Tamanho do núcleo e concentração no controlador; propagação de dependências de um nível; E2E só no Chrome; backend de referência não pronto para produção distribuída. Ver cap. 34.
O que seria necessário para suportar um caso ausente — por exemplo, progresso por arquivo sem chunks?
Enviar cada arquivo em uma requisição própria (um transporte registrado que faça N requisições e agregue onUploadProgress) e um contrato de backend para vincular os arquivos ao registro — é o padrão que o módulo de chunks já segue com tokens.
